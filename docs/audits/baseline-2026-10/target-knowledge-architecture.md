## Design principles

1. **One authority per concern.** OpenSpec owns maintained behavior only after a reviewed capability transfer. The frozen OpenAPI YAML, Java contracts, architecture/data documents, decision register, verification evidence, and release gate retain their own authority.
2. **No false as-built claims.** Target architecture, source presence, production composition, executed verification, and release acceptance remain separately labeled.
3. **Preserve provenance.** Legacy source documents, identifiers, approvals, decisions, and historical evidence remain reachable while a successor is introduced.
4. **Incremental and reversible.** No mass move, deletion, or link breakage. A capability transfer is an additive, reviewed change with a registry record and a rollback path.
5. **One modular monolith.** Documentation describes FinFast's in-process Java modules and single logical database, not fictional services, brokers, or distributed ownership.
6. **Native tool boundaries.** OpenSpec manages specifications and change-local work. A later harness manages safe execution and handoff. GitHub manages shared ownership, review, and merge gates.

## OpenSpec boundary and actual workflow

The installed OpenSpec CLI reports the default spec-driven schema with four artifacts: proposal, specs, design, and tasks. It supplies commands to initialize a project, inspect specs and changes, validate, show artifact completion status, and archive a completed change while updating main specs.

For FinFast:

- Main specifications under openspec/specs are the maintained behavioral authority only for a capability whose transfer is recorded and approved.
- Active changes under openspec/changes are bounded proposals and change-local design/task records. They do not replace the decision register or project backlog.
- Archive is used only after the OpenSpec change is complete, verified as appropriate, reviewed, and its durable-document impact is applied. The installed archive command updates main specs unless a justified documentation-only change uses its documented skip-specs option.
- OpenSpec validation is structural workflow evidence, not proof of tests, financial correctness, security, or release acceptance.

## Future harness boundary

| Native OpenSpec | Future custom harness | Team and GitHub |
|---|---|---|
| Main behavioral specs, proposal/spec/design/tasks artifacts, artifact status, validation, archive. | Safe startup checks, bounded worktree policy, approved command selection, local execution claims, deterministic handoff, and recovery instructions. | Issue ownership, PR review, branch protection, shared coordination, CI checks, and merge authority. |

A local execution-state file cannot provide a distributed work lock. The custom harness must instead show current branch/worktree/status, provide an advisory one-change rule, and defer shared exclusivity to assigned issues, pull requests, and review policy.

## Walking Labs assessment

The official Walking Labs Learn Harness Engineering repository describes harness-creator as a scaffold for AGENTS.md, feature lists, initialization, and verification workflow artifacts. It is useful later as a read-only audit checklist or a throwaway-worktree scaffolding comparison, not as an automatic installation path. FinFast already has substantial AGENTS.md, Makefile, Maven Wrapper, CI, and documentation-routing foundations. Any generated output must be inspected, minimized, reconciled with those sources, and reviewed in a dedicated harness change after the documentation migration.
